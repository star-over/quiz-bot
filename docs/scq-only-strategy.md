# Стратегия SCQ-only: обоснование и выводы

## Контекст

Принято решение сфокусироваться на единственном техническом типе вопросов — SCQ (Single Choice Question), максимально развивая его потенциал. Решение основано на анализе исследований (см. `docs/question-type-diversity-research.md`) и специфики продукта (Telegram-бот, один разработчик, добровольное участие).

---

## 1. Два измерения типов вопросов

### Технический тип — UI/механика взаимодействия

Как пользователь физически отвечает на вопрос.

| Техн. тип | Механика | Статус |
|-----------|----------|--------|
| **SCQ** (Single Choice) | Inline keyboard, один ответ | Основной тип |
| **Yes/No** | 2 кнопки, бинарный выбор | Обучающая механика |
| MCQ (Multiple Choice) | Несколько ответов + «Готово» | Не планируется |
| Free text input | ForceReply, ввод текста | Отложено |
| Ordering | Последовательный выбор | Отложено |
| Matching | Соединение пар | Отложено |

### Логический тип — когнитивный процесс

Что именно тренируется, какая формулировка. Реализуется через **контент**, не через код.

| Лог. тип | Техн. тип | Уровень Блума | Пример |
|----------|-----------|---------------|--------|
| Vocabulary | SCQ | Remember | «Что значит "give up"?» |
| Cloze (заполни пропуск) | SCQ | Apply | «She ___ every day» → варианты |
| Error correction | SCQ | Analyze | «Какое предложение правильное?» |
| Translation | SCQ | Apply | «Переведите: Я иду домой» → варианты |
| Grammar rule | SCQ | Remember/Understand | «Какое время используется?» |
| Введение нового материала | Yes/No | — | «"To give up" = "сдаться". Верно?» |

**Ключевой вывод:** расширение логических типов (контент) не требует изменений в коде. Один технический тип SCQ покрывает уровни Блума от Remember до Analyze через разные формулировки.

## 2. Аргументы за SCQ-only

### 2.1. Инженерная простота

Один code path, один handler, одна машина состояний, один тип клавиатуры. Меньше кода = меньше багов, быстрее итерации. Для проекта с одним разработчиком это решающий фактор.

### 2.2. Простой UX как конкурентное преимущество

Простой UI + сложная логика под капотом (IRT, адаптивность, interleaving). Пользователь не распыляется на освоение разных механик. Разработчик не распыляется на реализацию разных UI-flow. Онбординг = ноль: первый вопрос понятен без инструкций.

### 2.3. Управляемый параметр guessing

Параметр guessing (c ≈ 1/n) — не константа, а управляемый рычаг адаптивного алгоритма. Имея пул из 10+ дистракторов, алгоритм может подавать 3, 5 или 8 вариантов в зависимости от задачи: меньше вариантов = легче, больше = сложнее. Это расширяет пространство сложности внутри одного технического типа.

### 2.4. Моторный паттерн как фича

Стабильный моторный паттерн (прочитай → нажми кнопку) = низкое трение = больше вопросов на единицу времени. Для Telegram-бота, где сессия — 2–5 минут, throughput важнее depth: 15 SCQ за 3 минуты > 3 free-text за 3 минуты.

### 2.5. Telegram-нативность

Inline keyboard — самое естественное взаимодействие в Telegram. ForceReply ощущается чужеродно, ordering — неуклюже. SCQ идеально ложится в платформу.

### 2.6. Простая IRT-калибровка

Все айтемы в одном формате — не нужны отдельные IRT-модели по техническим типам. Адаптивный алгоритм проще и точнее. При этом параметр guessing управляется через количество вариантов.

## 3. Роль Yes/No — обучающая механика

### Ключевое разделение целей

| Техн. тип | Цель | Guessing = проблема? |
|-----------|------|---------------------|
| **SCQ** | Тестирование и закрепление (retrieval practice) | Да, управляем через n |
| **Yes/No** | Введение нового материала (exposure) | Нет — мы не измеряем, мы знакомим |

Yes/No — это не тест, а **микро-урок в формате вопроса**. Пользователю нет необходимости вчитываться в варианты ответов. Это минимальная когнитивная нагрузка для максимально нового контента.

Пример: «Знаете ли вы, что "to give up" означает "сдаться"?» → Да/Нет → В любом случае показываем объяснение с примерами.

Guessing = 50% здесь не проблема: мы и так знаем, что это новый для пользователя материал. Через простой тест рассказываем ему новые вводные.

## 4. Известные ограничения и их митигация

### 4.1. Потолок recognition

SCQ — recognition-based формат (g=0.36 в лабораторных условиях). Однако:
- Увеличение количества вариантов повышает сложность
- Усложнение дистракторов (близкие по смыслу, исключения, нюансы) сдвигает фокус от простого узнавания к анализу
- Тестирование не «goes vs go», а особенностей использования, исключений, контекстных различий

### 4.2. Разрыв с production

SCQ не тренирует production (говорение, письмо). Принятое решение: мириться на текущем этапе. В будущем — голосовой ввод (аудиосообщения) как отдельная production-механика.

### 4.3. Пол случайного угадывания

Митигация: а) увеличение количества вариантов, б) несколько вопросов по одной теме, в) статистический анализ паттернов ответов.

### 4.4. Неполное покрытие skillVector

SCQ покрывает grammar, vocabulary, reading. Listening — через аудио + SCQ (ответ всё ещё кнопкой). Speaking — отложено до введения голосового ввода.

## 5. Гипотеза селектирования

### Суть

Исследования показывают g=0.81 для production vs g=0.36 для recognition. Но эти данные получены в лабораторных условиях, где участники **не могут уйти**. В реальном продукте (Telegram-бот, добровольное участие) эффект confounded self-selection bias:

- Пользователи, готовые к сложным механикам (free text) — **самоотобранная группа** с высокой мотивацией
- Их результаты лучше не (только) из-за механики, а из-за мотивации
- Немотивированные пользователи при столкновении с friction просто уходят, показывая не «меньшее обучение», а **нулевое**

### Формула реального обучения

```
Реальное обучение = эффективность_механики × retention_rate × частота_использования
```

Условный расчёт:

| Механика | Эффективность | Retention | Частота | **Итого** |
|----------|--------------|-----------|---------|-----------|
| Production (free text) | 0.81 | 0.3 | 3 р/нед | **0.73** |
| SCQ | 0.36 | 0.8 | 5 р/нед | **1.44** |

Production эффективнее per-question, но SCQ эффективнее per-user из-за более высокого retention и частоты использования.

### Нюанс

Generation effect (production > recognition) — реальный когнитивный механизм, а не только статистический артефакт. Мозг создаёт более глубокие следы в памяти при порождении ответа. Но этот эффект реализуется **только если пользователь продолжает заниматься**. Лучшая механика — та, которую пользователь реально использует регулярно.

### Поддержка из индустрии

Duolingo в своих исследованиях показывает, что **главный предиктор обучения — consistency** (ежедневное возвращение), а не тип упражнения. Аналогия из медицины: «intention to treat» vs «per protocol» анализ — если считать только дошедших до конца, лечение кажется эффективнее, чем оно есть.

## 6. Стратегия развития

### Сейчас
- SCQ как основной технический тип для тестирования и закрепления
- Yes/No как обучающая механика для введения нового материала
- Расширение логических типов через контент (cloze, error correction, translation)
- Фокус на адаптивном алгоритме (IRT, desirable difficulty)

### Среднесрочно
- Аудио-вопросы (listening) с ответом через SCQ
- Управление количеством вариантов как рычаг адаптивной сложности

### Долгосрочно (по данным retention/engagement)
- Голосовой ввод (production-механика для speaking)
- Оценка потолка recognition по данным пользователей
