# Концепция использования XState в Quiz Bot

## Введение

В этом документе описывается концепция использования библиотеки XState для реализации бизнес-логики в Telegram боте для викторин. XState позволяет создавать конечные автоматы (state machines), которые обеспечивают предсказуемое и управляемое поведение приложения.

## Архитектура XState компонентов

### 1. Машина-менеджер (Session Manager)

Машина-менеджер отвечает за управление состоянием пользовательской сессии викторины и координирует работу других машин, управляя их состояниями.

#### Основные функции:
- Проверка наличия сохраненного состояния в базе данных при поступлении сообщения
- Загрузка сохраненного состояния и продолжение выполнения с текущего места
- Запуск новой сессии машины-роутера, если сохраненное состояние отсутствует
- Сохранение текущего состояния машины в память
- Удаление данных сессии из памяти при завершении работы машины
- Передача сообщения пользователя в загруженную машину
- Подписка на специальные события дочерних машин для сохранения состояния

#### Состояния машины-менеджера:
- `idle` - Ожидание сообщения от пользователя
- `searching` - Поиск в базе состояния дочерней машины для пользователя (`routing`- если не найдено)
- `loading` - Загрузка сохраненного состояния дочерней машины из базы
- `starting` - Запуск дочерней машины в памяти
- `hydration` - Приведение дочерней машины в загруженное из базы состояние
- `userInteraction` - Передача сообщения пользователя в дочернюю машину
- `processing` - Ожидание процесса обработки сообщения пользователя дочерней машиной
- `routing` - Если дочерняя машина завершилась, то запуск машины роутера для подбора вопроса для пользователя, с передачей состояния новой дочерней машины в машину менеджера
- `saving` - Сохранение нового состояния дочерней машины в базу данных
- `killing` - Очистка данных дочерней машины из памяти 

#### Переходы:
- `RECEIVE_MESSAGE` - Получение сообщения от пользователя
- `STATE_NOT_FOUND` - Состояние дочерней машины не найдено в базе
- `STATE_LOADED` - Состояние дочерней машины успешно загружено
- `CHILD_MACHINE_STARTED` - Дочерняя машина успешно запущена
- `CHILD_MACHINE_HYDRATED` - Дочерняя машина приведена в загруженное состояние
- `USER_INTERACTION_COMPLETE` - Обработка сообщения пользователя завершена
- `CHILD_MACHINE_FINISHED` - Дочерняя машина завершила работу
- `ROUTER_STARTED` - Машина-роутер запущена
- `STATE_SAVED` - Состояние успешно сохранено в базу
- `CHILD_MACHINE_KILLED` - Дочерняя машина удалена из памяти

### 2. Машина-роутер (Question Router)

Машина-роутер отвечает за выбор следующего вопроса в викторине и его представление пользователю.

#### Основные функции:
- Определение следующего вопроса на основе текущего состояния
- Запуск типа дочерней машины в соответствии с вопросом
- Инициация дочерней машины вопросом
- Старт дочерней машины для взаимодействия с пользователем
- Передача контекста дочерней машины в машиную менеджера для сохранения состояния

#### Состояния машины-роутера:
- `idle` - Ожидание
- `selecting` - Выбор следующего вопроса
- `starting` - Запуск дочерней машины нужного типа с текущим вопросом
- `transfer` - Передача текущего (начального) состояния в машину менеджера для сохранения в БД

#### Переходы:
- `QUESTION_SELECTED` - Вопрос успешно выбран
- `CHILD_MACHINE_STARTED` - Дочерняя машина вопроса запущена
- `STATE_TRANSFERRED` - Состояние передано в машину-менеджер

### 3. Машины-вопросы (Question Types)

Для различных типов вопросов создаются специализированные машины:

#### 3.1. Вопрос с одиночным выбором (Single Choice Question)

##### Состояния машины вопроса с одиночным выбором:
- `asking` - Представление вопроса с вариантами ответа
- `evaluating` - Оценка выбранного ответа
- `feedingBack` - Обратная связь (coorect / error + hint)

##### Переходы:
- `QUESTION_ASKED` - Вопрос представлен пользователю
- `ANSWER_SELECTED` - Пользователь выбрал вариант ответа
- `ANSWER_EVALUATED` - Ответ оценен
- `FEEDBACK_PROVIDED` - Обратная связь предоставлена пользователю

#### 3.2. Вопрос с множественным выбором (Multiple Choice Question)

##### Состояния машины вопроса с множественным выбором:
- `asking` - Представление вопроса с вариантами ответа
- `collecting` - Сбор ответов пользователя, петля, до спец комманды что это ответ.
- `evaluating` - Оценка выбранного ответа
- `feedingBack` - Обратная связь (coorect / error + hint)
- `evaluating` - Оценка выбранных ответов

##### Переходы:
- `QUESTION_ASKED` - Вопрос представлен пользователю
- `ANSWER_SELECTED` - Пользователь выбрал вариант ответа
- `ANSWERS_SUBMITTED` - Пользователь подтвердил ответы
- `ANSWERS_EVALUATED` - Ответы оценены
- `FEEDBACK_PROVIDED` - Обратная связь предоставлена пользователю

## Интерфейсы дочерних машин

### Интерфейс взаимодействия с Telegram
Дочерние машины используют этот интерфейс для отправки сообщений в мессенджер:
- `sendMessage` - отправка нового сообщения
- `updateMessage` - обновление существующего сообщения
- `renderQuestion` - рендеринг вопроса в формате Telegram
- `renderFeedback` - рендеринг обратной связи

### Интерфейс взаимодействия с менеджером
Дочерние машины используют специальные события для уведомления менеджера:
- `xstate.manager.state.changed` - изменение состояния машины
- `xstate.manager.user.interacted` - взаимодействие пользователя с вопросом
- `xstate.manager.question.answered` - пользователь ответил на вопрос
- `xstate.manager.feedback.sent` - отправлена обратная связь
- `xstate.manager.session.completed` - сессия завершена

Менеджер подписывается на эти события и при их наступлении сохраняет состояние дочерней машины в базу данных.

## Интеграция с Convex

### Сохранение и восстановление состояния

Состояние машин будет сохраняться в базе данных Convex в коллекции `quizSessions`:

```typescript
// Расширенная схема для хранения состояния машины
quizSessions: defineTable({
  quizId: v.id("quizzes"),
  userId: v.id("users"),
  startedAt: v.number(),
  finishedAt: v.optional(v.number()),
  score: v.optional(v.number()),
  // Новые поля для хранения состояния XState
  xstate: v.optional(v.object({
    sessionId: v.string(),
    state: v.string(), // Сериализованное состояние машины
    context: v.any(),  // Контекст машины
    lastUpdated: v.number(),
  })),
}).index("by_user", ["userId"])
  .index("by_quiz", ["quizId"]),
```

### Взаимодействие компонентов

1. При получении сообщения от пользователя, обработчик вызывает машину-менеджер
2. Машина-менеджер переходит в состояние `searching` и проверяет наличие сохраненного состояния дочерней машины в базе данных
3. Если состояние существует, машина-менеджер переходит в состояние `loading` и загружает состояние дочерней машины
4. Если состояние отсутствует, машина-менеджер переходит в состояние `routing` и вызывает машину-роутер для выбора вопроса
5. Машина-менеджер переходит в состояние `starting` и запускает дочернюю машину (вопроса или роутера)
6. Машина-менеджер переходит в состояние `hydration` и приводит дочернюю машину в загруженное состояние (если оно было загружено)
7. Машина-менеджер переходит в состояние `userInteraction` и передает сообщение пользователя в дочернюю машину
8. Машина-менеджер переходит в состояние `processing` и ожидает завершения обработки сообщения дочерней машиной
9. Если дочерняя машина завершила работу, машина-менеджер переходит в состояние `routing` и вызывает машину-роутер для выбора следующего вопроса
10. Машина-менеджер переходит в состояние `saving` и сохраняет новое состояние дочерней машины в базу данных
11. Машина-менеджер переходит в состояние `killing` и удаляет данные дочерней машины из памяти

## Примеры использования

### Пример 1: Начало новой сессии викторины

1. Пользователь отправляет команду `/quiz`
2. Обработчик команды вызывает машину-менеджер
3. Машина-менеджер переходит в состояние `routing`, так как состояние дочерней машины отсутствует в базе
4. Машина-менеджер запускает машину-роутер для выбора первого вопроса
5. Машина-роутер выбирает первый вопрос и запускает соответствующую машину-вопрос
6. Машина-менеджер передает управление машине-вопросу для взаимодействия с пользователем
7. После обработки ответа состояние сохраняется в базе данных

### Пример 2: Продолжение сохраненной сессии

1. Пользователь отправляет любой текст после перезапуска бота
2. Обработчик сообщения вызывает машину-менеджер
3. Машина-менеджер переходит в состояние `searching` и проверяет наличие сохраненного состояния дочерней машины в базе данных
4. Если состояние найдено, машина-менеджер загружает его и приводит дочернюю машину в это состояние
5. Машина-менеджер передает сообщение пользователя в дочернюю машину для обработки
6. После обработки ответа состояние сохраняется в базе данных

## Преимущества подхода

1. **Предсказуемость**: Все возможные состояния и переходы явно определены
2. **Управляемость**: Легко отслеживать текущее состояние системы
3. **Расширяемость**: Новые типы вопросов и функциональность могут быть добавлены как новые машины
4. **Надежность**: Встроенная обработка ошибок и неожиданных состояний
5. **Тестируемость**: Каждое состояние и переход может быть протестирован отдельно
6. **Восстанавливаемость**: Возможность сохранения и восстановления состояния обеспечивает непрерывность пользовательского опыта

## План реализации

1. Создать базовые машины XState для каждого компонента
2. Реализовать логику сохранения и восстановления состояния
3. Интегрировать машины с существующими обработчиками Convex
4. Протестировать взаимодействие компонентов
5. Оптимизировать производительность и обработку ошибок
