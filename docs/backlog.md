## Пул дистракторов и адаптивный выбор вариантов ответа

**Статус:** отложено
**Дата:** 2026-03-26

Вместо фиксированного набора из 4 вариантов — хранить пул из 6–10 дистракторов на вопрос и при каждом показе случайно выбирать N из них. Снижает эффект запоминания конкретного набора вариантов.

Дополнительно: адаптировать количество показываемых вариантов по `known`:
- `known < 0.5` → 3 варианта (GUESS=0.33, мягче при обучении)
- `known ≥ 0.5` → 4 варианта (GUESS=0.25, точнее при закреплении)

### Почему отложено

- Разница GUESS=0.33 vs 0.25 даёт ~0.05 в обновлении `known` — несущественно на данном этапе
- Требует `displayCount` поля на вопросе чтобы GUESS оставался предсказуемым для BKT
- Все дистракторы должны быть равной «коварности», иначе случайный набор даёт непредсказуемую сложность
- Explanation нужен для каждого из 10 дистракторов — большой объём контентной работы

### Что нужно для реализации

- Поле `displayCount: number` на вопросе (сколько вариантов показывать)
- Логика случайного выбора N из `choices` в `QuestionManager` (правильный ответ всегда включается)
- Передавать реальный `choicesCount` в BKT-обновление, а не брать из длины массива

## Задержка перед следующим вопросом

**Статус:** отложено
**Дата:** 2026-03-22
**Связано с:** напоминания, периодическое обучение, контроль темпа

### Проблема

Следующий вопрос приходит сразу после фидбека. Пользователь не успевает изучить объяснение.

### Загрязнение данных

`shownAt → respondedAt` измеряет время на вопрос. Если фидбек и следующий вопрос видны одновременно, пользователь тратит часть этого времени на чтение фидбека — данные для IRT-калибровки контаминируются. Нет способа разделить «думал над вопросом» и «изучал фидбек на предыдущий».

### Техническое решение

Convex `ctx.scheduler.runAfter()`. Задержку делать динамической (по длине explanation). Нужен отдельный `internalAction` с собственным grammY `Api` инстансом, хранение `scheduledId` для отмены при `/start`, `/stop`, `/test`.

### Почему отложено

- Фидбек остаётся в чате (не пропадает), проблема скорее в ощущении
- Нет данных о реальном поведении пользователей
- Реализация добавляет ~100 строк + schema change + race condition handling
- Логически относится к тому же блоку что напоминания и периодическое обучение

## Zod как единый источник истины для TypeScript-типов и Convex-схем

**Статус:** отложено
**Дата:** 2026-03-26

### Суть

Сейчас структура полей описана в двух местах: `seed/schemas.ts` (Zod) и `convex/schema.ts` (Convex validators). Базовые типы полей дублируются вручную. Цель — сделать Zod единственным источником истины: TypeScript-типы и Convex validators генерируются из Zod-схем автоматически.

### Архитектура

```
seed/schemas.ts (Zod — поля + описания + seed-валидация)
    ├── z.infer<> → TypeScript типы (уже работает)
    ├── zodToConvex() → Convex validators → + индексы вручную → schema.ts
    └── .extend() + .refine() → дополнительная seed-валидация (Telegram HTML, cross-ref)
```

### Инструменты

`convex-helpers` (официальная библиотека Convex) — модуль `zod4` для Zod v4:
- `zodToConvex()` — конвертирует Zod-схему в Convex validator для аргументов функций
- `zodOutputToConvex()` — конвертирует для определения таблиц
- `zid("tableName")` — маппинг `z.string()` → `v.id("tableName")`

### Ограничения

- Индексы (`.index(...)`) остаются только в `convex/schema.ts` — в Zod не выражаются
- `v.id("tableName")` требует `zid()` из `convex-helpers` — добавляет зависимость
- Кастомные refinements (Telegram HTML) не транслируются в Convex — остаются в Zod

### Почему отложено

- Текущий масштаб схемы (~10 таблиц) не создаёт реальной боли от дублирования
- Добавляет зависимость и косвенность в `convex/schema.ts`
- Вернуться когда схема разрастётся и ручная синхронизация станет ощутимой проблемой
